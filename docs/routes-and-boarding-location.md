# Routes and Boarding Location

## Approved behavior

- A bus may have zero or more active routes at the same time.
- A route may be assigned to multiple buses.
- Boarding permission is the union of active-route employee permissions.
- Assignment timestamps are system-managed audit data; there is no route schedule UI.
- Device configuration uses a monotonically increasing bus configuration version. The
  Android app acknowledges a version only after its Room transaction succeeds.
- Offline devices continue to use the last successfully applied configuration.

## Stop catalog

- Stops are shared records. Routes store only ordered stop IDs; the same stop can
  be used by multiple routes and cannot appear twice in one route.
- Stop codes are generated by the server (`STOP-000001`, etc.) and are read-only
  in the Admin UI. Stop names do not need to be unique.
- Stop management is reached from `Routes > Stops`, not from a top-level tab.
  Route editing searches active existing stops and can create a stop when none
  matches. Route editing only adds, removes, or reorders stops.
- A stop can be selected on the map by clicking or dragging the marker. Latitude,
  longitude, and the radius circle stay synchronized. A new stop defaults to the
  first stop of the route, or Hanoi (`21.0278, 105.8342`) at zoom 13 when the
  route has no stops.
- Editing a shared stop warns which routes are affected and advances the device
  configuration version for their assigned buses. Inactive stops remain in
  existing routes and history but are unavailable for new route assignments.

## Boarding events

The Android app makes one location request per scan and waits at most 500 ms. A
successful result is stored as `CURRENT`; otherwise the newest Android last-known
location is stored as `SNAPSHOT`; if neither exists the source is `UNAVAILABLE`.
The NFC decision is displayed immediately and does not wait for location.

Events retain employee number, name, and department snapshots, raw location and
accuracy, the route associations in effect at scan time, and an optional matched
stop. A snapshot older than 30 seconds or a location with accuracy worse than 100 m
is retained but is not assigned to a stop. Event type is currently always
`BOARDING`; `ALIGHTING` is reserved for future automatic inference.

The Admin boarding-event table shows scan time, employee number, employee name,
employee department, result, route, and stop. Technical fields are shown only in
the expandable detail.

## Route history

Route history remains a bus-and-date query. It does not calculate mileage per
route. Daily mileage is GPS-estimated from consecutive bus points; segments that
imply a speed over 150 km/h or have accuracy worse than 100 m are excluded. Hovering
a GPS point displays its local `HH:mm` time.
